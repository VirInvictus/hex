# Discworld official documentation: research findings

Source: `testing_facility/discworld-docs/`: the official /lpc/playing and /lpc/about pages plus the full documentation.c tree (concepts 293, helpdir 230, known_command 99, object 98, room 67, newbie 16, rituals 7, spells 2, plus 873 playing pages; 1,721 pages total, crawled 2026-11-05, zero errors). Three research sweeps (protocols & formats, rules & policy, gameplay systems) read the corpus against our phase designs. This document is the merged, authoritative result; per-phase corrections have been folded into the phase docs with pointers here.

## 1. The headline: the automation page inverts our walker design

`concepts/automation` ("Client-side Automation") is a standalone rules page our docs had never cited, and its speedwalk ruling is precise:

Against the rules (verbatim): *"Using a client-side speedwalking feature that sends direction commands room by room, since this causes your character to send commands -- and therefore unidle -- without your direct input."* And: *"the 'slow' kind, where the route you take may be recalculated if you for instance wimpy out of a room, is not allowed because it keeps sending commands; the 'fast' kind, where all route commands are sent in one go and cannot be altered afterwards (other than by manually sending 'stop'), is allowed. Like aliases, if such a speedwalk takes more than 5 minutes to execute, the MUD will eventually abort it due to inactivity."*

The core litmus test: *"nothing is sent to the MUD that causes your character to unidle without you taking an action to send it at the same time. Put differently, if you suddenly disappeared and yet your character unidled after that, you were breaking the rules all along."* (Pit's Rules, `concepts/pit's_rules`, restates this as enforcement doctrine (the "Aliens" rule).)

**Consequence:** Phase 2's verify-every-step walker is, in the MUD's own vocabulary, the banned "slow" kind (each step is sent because the previous room.info arrived, not because the user just acted) The design is inverted: `/goto` becomes a **one-shot batch queue**: send the travel-mode option and all route commands in one go on the single user invocation, abortable only by the user typing `stop` (or `/stopwalk`, which sends `stop` from the alias). Identifier verification becomes **post-hoc drift reporting** (the map sends arrive as the queue executes; Hex displays "expected vs actual" and never re-sends). Routes longer than ~4 minutes of steps get a warning that the MUD will abort the queue at 5. This also kills the stall-timer machinery and the Phase 5 journey-branch (a batched queue has no per-step expectation to violate).

**Everything else in the spec's invariant is CONFIRMED by the primary source**: the unidle test, the blank-line example ("even an empty line causes you to go unidle"), the GMCP/ZMP restatement ("Triggers and timers which send anything that could make your character unidle are not allowed. This includes blank lines!"), and the explicit allow-list (colour triggers, sound triggers, MUD-side long aliases, telnet keepalives (*telnet codes only*, never an empty line)).

**Second clause discovered: the trivialising ask** (output-side, not just input-side): *"A plugin which gives you a number of buttons, and highlights the one you should press next depending on the progress of a task"* is a named example of trivialising the game, with the note that it *"primarily applies to players writing advanced scripts or client-side plugins*"; this is Hex's exact category. Data display (vitals, Quow records, timers, XP/hour, routes) is clearly fine; anything that outputs "you should now do X" (a TM recommender that picks your next skill, mission solution hints) is exposed. Posture: keep every feature informational, cite the page's own escape hatch ("if you are in doubt … talk to a liaison") in the spec.

**Awareness rule** (also from this page): *"Running commands from a client that only shows you two lines of output"* and *"sending all tells and souls to a separate window, and minimising that window"* are against the rules. UI constraint for Hex: a chat tab is fine; a design that buries tells out of sight is not. Also: auto-reconnect on idle-out/quit is explicitly banned ("some clients do this by default if you save your password"); Hex must never grow one.

## 2. Protocol and format facts

- **Handshake confirmed verbatim** (concepts/gmcp): `core.hello { "client": ..., "version": ... }` then `core.supports.set [ "char.login", "char.info", "char.vitals", "room.info", "room.map", "room.writtenmap" ]`; the six commands with timing (login, login, per-command, look/glance/enter × 3); room.info carries name, identifier, status ("e.g. inside, outside, underwater"; **`outside` is officially documented**, extending our kind vocabulary) and a visibility flag; room.map "may be empty if vision is bad (for instance in the case of snow)" and includes colour codes "unless you have maps set to plain (see options output map)". No payload schemas beyond prose; no other GMCP commands exist.
- **Confirmed absent from the entire corpus**: MSDP, ATCP, MSSP, NAWS documentation, telnet charset negotiation. ZMP exists (concepts/zmp) as the legacy twin of GMCP (same six commands, `zmp.ident` handshake, vitals without alignment).
- **MCCP** (concepts/compression, helpdir/mccp): ~20% bandwidth reduction, **login-queue priority** for MCCP clients, `mccp` command output documented (usable as a `/hexcheck` row). Connection facts for the README: port 23 or 4242, IPv6 only on 4242, **TLS on 4245**.
- **MXP is a fully documented subsystem** (concepts/mxp, helpdir/mxp): `term mxp`, 24-bit `#RRGGBB` colour, clickable links, dropdown menus, `mxp restore` after netdead colour loss. Phase 7's theme work assumed only local ANSI painting, but the MUD natively offers 24-bit colour on a `term mxp` terminal.
- **The colour system is enormous and documented** (helpdir/colours, concepts/colour_list, concepts/usercolour, concepts/zmud_colours): ~250 named colours mapped exactly onto xterm256, hex codes (`#FFBF00`, backgrounds `B_#004225`), `ansi*` override tokens, per-event `options colour`, per-club/per-inform/per-talker-channel colour trees, `colours test <colour>` previews, and the `%^OPTION%^...%^RESET%^` usercolour grammar our setup strings use (upper case, no spaces; `options output usercolour=on` reveals them). Phase 7's theme could adopt the official "Recommended Colours" set.
- **Options system**: `options <option>`, `options <option> = <value>`, `options set <option> <quoted>`, `all` wildcard for setting only. Documented output shape is space-separated (`output : / look brief / combat verbose`) **without** `=`, though helpdir/tactics shows `attack = left`; mixed shapes per tree, so `/hexcheck`'s parser stays live-verified. Invalid `rows` values reset to **24** (footgun for `rows 999`: prefer `options terminal rows=999`, which is the documented syntax). `options output map plain = on` is officially documented (**Phase 5's open question is answered: yes, a plain option exists**). Lookmap knobs (`output map look|lookcity|glance|glancecity`) control the inline look maps tt_dw's setup disables.
- **Confirmed absent from official docs** (tt_dw/community knowledge remains the only source, keep attribution): `brief exits`, `automatic rows`, the skills list/branched round-trip, `check quota` output, job-market boards and `apply for`, `gp brief`, club/talker/shout receive formats, the idle-out timeout value (only the "empty line every 29 minutes" example implies ~30 minutes), TPA entirely, mission mechanics entirely ("cooldown" has zero hits), thief quota mechanics beyond three sentences, broomstick charges, the mindspace word and `+30`, bonus/cost formulas, per-spell pages (the spells tree is 2 AshkEnte pages), tracked-ritual pages (only the remember-place/ward family is documented), stat items, bugshield nouns, FTF, journey arrival lines, ferries, room kinds beyond inside/outside/underwater.

## 3. Command formats (helpdir): the load-bearing set

- **score**: `score [brief|verbose] [stats|quests|align|relationships|fighting|temperature|burden]`. `score brief` documented as `Hp: 913 (1040) Gp: 122(122) Xp: 36190` (note space inside HP parens, none in Gp, single-space gaps, **no Burden field** contradicts phase-6's regex; wire-verify). `score stats` is a **3-line** dot-padded table (dot counts match our 3/6/3/7/9/9/9 exactly) and `score brief stats` a 2-line compact form; phase-3's one-line assumption needs the live check with cols set.
- **monitor/prompt**: `monitor [off|on|slow|snail's pace]`, `monitor show|default|<string>`; the `$`-code list is official ($hp$ $maxhp$ $gp$ $maxgp$ $xp$ $burden$ $temp$ $align$ $hurtcolour$ $servertime$ $localtime$ ...); prompt's `$hurtcolour$` closes with `%^RESET%^`. Monitor "goes on during combat" (out of combat the prompt is the feed is the prompt; Phase 6's fallback precedence is right). Default monitor uses single spaces; phase-6's three-space regex matches only after `/hexsetup`.
- **map**: `map`, `map text`, `map ascii`, `map door text`; legend `@` you (yellow), `+` Door, `*` Room, `-`/`|` exits, `$` Room with living things, `&` + non-cardinal exits; writtenmap grammar confirmed via the `map door text` example ("...the limit of your vision is one south and one southwest from here..."). Night/snow/rain shrink sight, so empty map payloads are expected, not errors.
- **shields** (not "check shields"; that two-word form appears nowhere): status of arcane and divine shields; example output includes condition lines and *"You will be protected for at least half an hour"* ("at least" duration wording matches the major-shield range parser).
- **hskills**: documented session skill-increase log (`adventuring.movement.riding.camel increased by 3 levels (and bonus 17) to level 4 (and bonus 23).`; brief form uses 2-letter components); a sanctioned fallback feed for Phase 3 goal alerts.
- **advance/skills**: `advance <skill> [by|to]` with best-match (`fi.p` → fighting.points); skills output shows level and bonus; branch gating is `depth*5` levels; `skillcap` exists (≥300, multiples of 25), and a capped skill's *used* level is the cap, which phase-3's parser should note.
- **teach/ETB: the one official formula, and it differs from tt_dw's**: *"the effective teaching bonus ... is the average of two numbers: (1) the bonus in the skill being taught, and (2) either the bonus in the relevant teaching skill, or twice the bonus in the taught skill, whichever is lower"*, capped; `teach specialise in <tree>` exists. Phase 3's `max_etb = max(bonus+200, bonus*1.5)` is a different shape, so `/skillcost` output must carry a caveat.
- **tell/talker/clubs**: `Pinkfish tells you: bing` confirmed; own-tell echo colon ambiguous between help pages (wire-verify); talker verbose officially `- (Two) Froggy's wispy voice comes from the bracelet saying : I am a blue frog!` (leading `- `, parenthesised channel, space before colon; **our regex needs updating**) and brief `(one) Feantur wisps: Ook!`; club-name display is player-configurable (`brief name`), so club regexes can never be canonical; `tell reply` remembers 15 minutes, `afk` injects a warning line ahead of your own echo.
- **gp**: `gp` documents per-channel availability lines (no `gp brief` documented); **shields**, **health all**, **condition [damaged] sorting**, **consider** (13-step ladder), **wimpy**, **tactics** (`options combat tactics attitude|response|focus|attack|parry|unarmed_parry`), **queue** (queue clears on excess length; max command limit), **resize**, **term** (`network` default negotiates both type and cols), **skillcap**, **memo** (announce-only precedent) all documented as above.

## 4. Gameplay systems vs our designs

- **Bonus formulas: officially nonexistent.** `concepts/bonus` says only that bonuses are affected by stats. The Jeanie piecewise and multiplicator stay community lore (attribution unchanged). Official anchors we gained: **stats start at 13** (confirms the golden-test constant), `rearrange` sets 8-23 with total ≤65, once ever; primaries are the ~14 deepest skills per guild, advanceable to **300** at minimum cost, branch categories cap at **50** (from helpdir/cost's `Cur/Max` board; also a fixture format); guild pages list category-level entries that mean "all children primary" (store that rule in hex_skilldata).
- **ETB** above; `concepts:taskmaster` names TM and its two thresholds (begin-succeed / always-succeed) with a chance between (no percentages; the stage arithmetic stays community-derived).
- **TPA, mission mechanics, quota mechanics, broom charges, mindspace formula, ritual durations, stat items, journey arrival lines: officially nonexistent.** Our colour→percentage map, 1-hour resets, quota parsers, broom triggers, `+30` mindspace, and major-shield approximation remain tt_dw-transcript-derived; the Phase 8 fixtures remain the verification path. The known-rituals tree covers only the remember-place/ward family (divine_guard, divine_sentinel, divine_hand, far_sight, modify_memento, raise_dead_pet, remember_place).
- **Mindspace dependency confirmed**: `known_command:remember`: *"Your capacity for remembering spells is determined by your skill bonus in magic.spells.special."* Skill choice official; `+30` not.
- **Spellcheck command documented**: 25 gp + 25 per stage cost, accuracy vs magic.spells.special, stage verdict wording ("you would most certainly succeed ... likely to fail"): a sendable fallback for Phase 4 if skills data is unavailable.
- **Death semantics**: spells detach on death (keep "a few"); rituals forgotten on death; hex_spells' known-store needs a death-purge hook.
- **Shields command name**: `shields` (no "check"); `meditate upon divine protection` officially clears all faith shields anywhere (a second resync verb for hex_charm).
- **Guild pages** (all 7): assassin 4 specs / 20 commands; thief 5 specs / 23; warrior 10 specs / 33; priest 7 deities, primaries include `faith.rituals.defensive.self`; witch 15 primaries including `magic.items.held.broom`; wizard 11 orders (the newbie page's "eight" is wrong; caution against single-page trust); fool 12 primaries. Feeds the guild-pack primaries dataset.
- **Travel**: `options personal travel = walk|journey` officially named (both values); walk = one step, journey = multi-step; carriage message set documented ("leaves the current stop / comes to a grinding halt / has arrived at X / next stop is Y"; "a new exit will appear in the room" when a carriage is in); ferries undocumented; **arcane transport NPCs** (`list / travel to <dest> / cancel`, A$20/A$10, language-gated) are a documented travel system absent from every design (a future `/path` annotation target).
- **Newbie essentials** officially recommends `term xterm256`, and `/hexsetup` should include it for parity. The official clients page endorses Quow's plugin ecosystem by name (MUSHclient + Quowbar) and the browser client; blightmud is not listed (expected).
- **UTF-8 since 2006** (`concepts/encodings`), so Lua string handling can assume UTF-8.
